# 萃取质量规约（Extraction Quality）

> CLI 只保证格式，记忆值不值钱取决于萃取业务事实的质量。写入任何记忆前先过本规约。
> 本文件是 maintain / conversation 写入前的强制自检清单（SKILL.md Workflow 引用）。
> 两套门槛：第一~四节管 **maintain**（交付后记业务变化），第五节管 **conversation --confirmed-fact**（对话中登记确凿事实）。

## 一、maintain 前五问自检

写 task-record 前，逐条回答以下五问。答不出第 1 问的，说明你在记 diff，不是在记业务记忆。

1. **用户最初的业务动机是什么？**（不是技术描述。"审核太慢导致设计师积压"是动机；"新增 review_stage 字段"不是。）
2. **哪条业务规则从什么变成了什么？**（写得出"从 X 变成 Y"才算业务变化；写不出就走 lite 档，别硬凑。）
3. **出现了哪些用户特有术语？**（"主管"在这个团队指什么岗位？哪个词的含义和字面不一样？术语进 conversation-record。）
4. **用户否定过什么？**（被拒绝的方案必须记 `--rejected`，防止未来会话把用户拒绝过的方案再提一遍。）
5. **这条记忆能让半年后的新会话少问用户哪个问题？**（回答不出来 → 这条记忆大概率是噪音，考虑不写或降为 lite。）

## 二、change-kind 判定步骤（配合 B4 语义合并）

提供 `--business-change` 前，**必须先读目标 domain 文件的"当前业务规则"段**，然后按序判定：

1. 列出该段现有的全部规则名（稳定 key）。
2. 本次变化是否废除某条现有规则？→ `--change-kind removed`，`--rule-name` 用现有规则名。
3. 本次变化是否修改某条现有规则的内容？→ `--change-kind modified`，`--rule-name` 用现有规则名（**不要**因为内容变了就换名，key 一经确立不变）。
4. 都不是 → 全新规则，`--change-kind added`，起一个稳定规则名：
   - 业务对象 + 主题的名词短语（"设计单审核流程"）；
   - 不含日期、动词、实现词（类名/表名/文件名）；
   - 一个规则只说一件事，两件事拆两个条目、两次 maintain。
5. `--scenario` 给一个具体例子，自检问题："一个没看过代码的人，能否据此判断系统行为是否符合规则？"

## 三、反模式清单（出现任何一条即返工）

- ❌ 把 diff 描述当业务变化（"修改了 WorkOrderService"不是业务规则）。
- ❌ 把技术重构写成业务规则（重构走 lite 档，业务行为没变就没有 `--business-change`）。
- ❌ 把猜测、讨论中的倾向写进 business-context（未落地不进真相层，红线 7）。
- ❌ 一次 maintain 塞多个不相关任务（一次交付一条记录，多任务拆开）。
- ❌ 标题写成"修改了 XX 文件"（标题写业务意图："设计单两级审核"）。
- ❌ modified 时不查规则名直接 added，造成同一规则重复条目（先读"当前业务规则"段！）。
- ❌ 把完整对话原文抄进记录（隐私默认 summary-only，红线 4）。

## 四、好/坏记录对照示例

### 示例 1：业务规则变化（full 档）

**✅ 好记录**

```
--title "设计单两级审核"
--summary "设计师提交后只有主管一审，经理发现漏批风险，要求增加经理终审兜底。"
--business-change "设计单最终通过必须依次经过主管审核和经理审核。"
--change-kind modified --rule-name "设计单审核流程"
--scenario "设计师提交后，主管一审通过、经理二审通过才进入已通过状态；任一级驳回整单退回。"
--implementation "审核状态机新增 manager-review 阶段，驳回统一回到待修改。"
```

为什么好：动机（漏批风险）、规则的从-到（单级→两级）、可判定的场景、稳定 key 复用，全部齐备。

**❌ 坏记录**

```
--title "修改 WorkOrderServiceImpl"
--summary "按用户要求改了审核代码。"
--business-change "增加了 review_stage 字段。"
--change-kind added --rule-name "2026-07 审核调整"
```

为什么坏：标题是文件名；summary 无动机；business-change 是实现细节不是业务规则；规则名含日期且不是名词短语；该走 modified 却用 added 制造重复条目。

### 示例 2：纯修复（lite 档）

**✅ 好记录**

```
--title "修复审核列表空指针"
--summary "审核列表在无历史记录时报错，用户要求修复。"
--implementation "对历史记录集合补空值判断。"
（不提供 --business-change → 自动 lite 档，只写 changelog）
```

**❌ 坏记录**

```
--title "修复审核列表空指针"
--business-change "审核列表不再报错。"
--change-kind added --rule-name "审核列表稳定性"
```

为什么坏："不报错"不是业务规则，是缺陷修复；硬凑 full 档会在真相层制造噪音条目，稀释真正的业务规则。

## 五、确凿性信号清单（事实登记门槛，F-007）

> 适用对象：`conversation --confirmed-fact`，把用户在对话中**确凿断言**的项目事实登记进真相层。
> 判定依据是**表述的确凿性**，不是事实的类型——业务规则、系统入口、配置值、术语锚点、代码约定都可以登记。
> 阈值**从严**：宁可漏记，不可误记。拿不准就不记，等下次用户再次确认。

### 5.1 只有这四类算确凿断言（✅ 可登记）

1. **陈述句 + 肯定语气，说的是项目当下的状态**——"设计单提交审核走的是 `/submitReview`"、"超时就是 30 秒"。
2. **纠正 AI 的错误认知**——"不是 A，是 B"。这是最强断言，优先登记。
3. **回答 AI 的事实性提问**——AI 问"这个字段什么含义"，用户给出答案。
4. **用户明确要求记住**——"记住这个"、"以后按这个来"。

### 5.2 这些一律不登记（❌）

- **疑问句**——"现在是不是会检查 BOM 为空？"用户在问，不是在告诉。
- **不确定措辞**——"应该是"、"我记得好像"、"大概"、"可能"。
- **讨论中的方案倾向**——还没定的事不进真相层（红线 7）。
- **AI 自己从代码反推的结论**——只能写进 conversation-record 的「仍未验证」段或 `--promote candidate`，**必须经用户确认后才能登记为事实**。代码是佐证，不是业务含义来源。
- **一次性的临时说明**——只对本次任务有效、下次会话用不上的信息。

### 5.3 同一句话里的成分要分开判定

用户原话：

> 「在设计单提交审核的时候，现在是不是会检查 BOM 是否为空？帮我检查一下这条链路 `http://.../liangang/workorder/submitReview`」

| 成分 | 判定 | 理由 |
|------|------|------|
| 「设计单提交审核……这条链路 `/submitReview`」 | ✅ 登记 | 用户在陈述这条业务的位置，是断言 |
| 「现在是不是会检查 BOM 为空」 | ❌ 不登记 | 疑问句，用户在问 |

结果只登记一条：`设计单提交审核入口 = POST /liangang/workorder/submitReview`。
BOM 校验那条要等**查完代码 + 用户确认"对，就是这样"**之后才能登记。

### 5.4 事实名是稳定 key

- 名词短语，描述**这是什么**，不含日期、不含值本身：`设计单提交审核入口` ✅ / `submitReview 接口` ❌ / `2026-08 的入口` ❌。
- 值变了**不要换名字**：同名再登记一次即可，CLI 自动覆盖旧值并把旧来源转入沿革。
- 事实**作废**（入口下线、配置取消）才用 `--retire-fact`；只是值变了用 `--confirmed-fact` 覆盖。
- 一次命令内的 `--fact-kind` 是共用的，类别不同的事实分两次命令登记；覆盖已有事实时不给 `--fact-kind` 会沿用旧类别。

### 5.5 何时提示用户

识别到确凿事实后，**不要打断当前对话另起一轮**，在当前回复末尾附一行确认即可：

> 📌 识别到 1 条待登记事实：设计单提交审核入口 = POST /liangang/workorder/submitReview。要登记吗？

用户确认后再执行 CLI。用户没回应就不写——**登记的前提永远是用户点头**。

### 5.6 锚点会腐烂

接口改名、配置调整后，登记的事实不会自动失效，`check` 也不校验它（CLI 零依赖、跨语言，不解析目标项目源码）。
**事实锚点是线索，不是保证。**读到事实后若与代码现状冲突，以代码为准并提示用户更新登记，不要默认记忆是对的。

## 六、一句话档位判定（B5）

> **半年后的新会话是否需要知道这次改动的"为什么"？** 需要 → full（给 `--business-change`）；不需要（纯修复/重构/杂务）→ lite（不给）。重大重构虽无业务变化但值得留档时，加 `--with-task-record`。
